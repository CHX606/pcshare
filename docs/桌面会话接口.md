# 桌面会话后端接口

这些 Tauri 命令可供 Windows 控制端页面接入。两端使用新版后端时，可在同一条已配对的 QUIC 连接上传送 H.264 视频和鼠标键盘输入。旧版被控端沿用已有的截图、点击及文字接口。查看本机仍使用原有的 `shot_capture`。

## 打开和关闭

| 命令 | 参数 | 返回值 |
| --- | --- | --- |
| `desktop_open` | `{ device, monitorIndex? }` 或 `{ device, hwnd }`。两者均省略时选显示器 0，窗口句柄是十进制字符串 | `Reply<{ sessionId, rawInput }>` |
| `desktop_next` | `{ sessionId }` | 成功时返回二进制 `ArrayBuffer`，失败时拒绝并给出 `{ code, msg }` |
| `desktop_input` | `{ sessionId, events }` | `Reply<null>` |
| `desktop_refresh` | `{ sessionId }` | `Reply<null>`，唤醒逐步模式下一次取图 |
| `desktop_close` | `{ sessionId }` | `Reply<null>`，同时取消正在等待的取帧 |

`desktop_open` 还可以带 `fitWidth`、`fitHeight`（本机屏幕的物理像素，只对显示器来源有效），让对方把这块显示器临时切到最接近的受支持分辨率。返回值多出 `fit: { applied, width, height, previousWidth, previousHeight, note? }`；没调成时返回 `fitError`，会话照常可用。详见下文“对方分辨率跟随本机”。

`Reply` 沿用现有接口的 `{ ok: true, data }` / `{ ok: false, err }`。后三个命令收到失效或属于其他窗口的会话编号时，以 `{ code, msg }` 拒绝调用。`rawInput` 表示对端支持原始鼠标键盘协议，操作是否获准由对端实时检查。显示器和窗口列表继续取自 `shot_monitors`。

打开后立即调用 `desktop_next`。首张 JPEG 用于在编码器启动期间先显示画面。每次处理完一帧再请求下一帧，同一会话允许一个在途取帧。逐步模式下，这个调用可以一直等待一次输入、手动刷新或链路恢复。输入走独立通道，可在等待画面时提交。切换设备、画面来源或离开页面时关闭原会话；恢复查看时重新打开。

## 二进制帧

前 4 字节为大端无符号整数 N。随后 N 字节是 UTF-8 JSON，其余字节为一张 JPEG 或一个完整 H.264 Annex B 访问单元。无需 Base64 转换。

| 元数据字段 | 用法 |
| --- | --- |
| `mode` / `format` | `step` / `jpeg` 或 `live` / `h264-annexb` |
| `timestampUs` / `key` | 微秒时间戳及关键帧标记。H.264 时间戳在同一编码周期内递增。JPEG 为截屏时刻 |
| `epoch` | 编码周期编号。编号变化时清空解码队列，用新周期首个关键帧重新配置解码器 |
| `codec` | 含 SPS 的 H.264 关键帧携带实际 AVC 编码字符串，例如 `avc1.42C028` |
| `encoder` / `reason` | 实际使用的编码器及逐步模式原因。正常首屏允许原因为空 |
| `transform` | 与旧版截图相同的驼峰字段。使用本帧的原点、原图宽高和实际显示矩形换算远端物理像素，多屏原点可为负值 |

坐标换算使用图像本身的显示矩形。先把指针在矩形内的位置换成 0 到 1 的比例，再把 X、Y 分别乘以原图宽高、向下取整，并限制在各轴的 `0…尺寸−1` 范围，最后加上 `originX`、`originY`。

实时帧可交给 WebCodecs `VideoDecoder`。用关键帧的 `codec` 开启低延迟解码，Annex B 模式不传 `description`。以 `key` 区分 `EncodedVideoChunk` 类型。关闭已绘制的 `VideoFrame`；页面失焦时发送 `release`。逐步帧可以直接作为 `image/jpeg` 显示。

## 输入

每批按顺序提交 1 至 64 个事件，等待上一批确认再发下一批。连续鼠标移动可以合并，按下和释放事件要保留顺序。所有 `x`、`y` 都是远端虚拟桌面物理像素。

| kind | 其他字段 | 说明 |
| --- | --- | --- |
| `move` | `x, y` | 移动与拖动 |
| `button` | `x, y, button, down` | 按钮为 `left`、`right`、`middle`。一次拖动使用按下、移动、释放 |
| `wheel` | `x, y, deltaX, deltaY` | Windows 滚轮单位，通常每格 120。纵向正值向上，横向正值向右 |
| `key` | `vk, down` | Windows 虚拟键码。可分别传递修饰键和普通键的按下与释放 |
| `click` | `x, y, button, double?` | 单击或双击，适用于逐步模式和旧版对端 |
| `text` | `text` | Unicode 文本，适合中文输入法提交后的文字 |
| `shortcut` | `combo` | 沿用现有的组合键名称，例如 `Ctrl+C` |
| `release` | 无 | 释放本会话仍按住的鼠标按钮和按键 |

逐步模式在一次完成的点击、滚动、文字、组合键或释放操作后回传截图。输入回执和图像走同一往返，页面通过正在等待的 `desktop_next` 取得图像。连续输入时只保留最新的操作结果。普通移动和按下不会单独要求截图。发送结果不确定时，先查看画面，避免重复发送点击或文字。

## 对方分辨率跟随本机

控制端在同一条连接上开一条 `desktop.display` 流，参数 `{ monitor, width, height }`，需要对方授予“截图”和“点按”权限，对方能力列表里有 `desktop.display.v1` 才发。被控端的处理：

| 步骤 | 做法 |
| --- | --- |
| 选模式 | 枚举这块显示器支持的模式（去掉隔行扫描）。有完全相同的分辨率就用它；否则在同宽高比里挑面积最接近的；都没有时，只有宽高比明显更接近才切换。刷新率尽量保持当前值，色深不变。旋转过的屏幕不动 |
| 切换 | 先用 `CDS_TEST` 试，再用 `CDS_FULLSCREEN` 临时切换，不写注册表，不改用户保存的显示设置。切换后等 0.8 秒再回话 |
| 保持 | 流一直开着。控制端关闭会话、连接断开、对方收回权限或开启“暂停被控”时结束；锁屏不结束 |
| 还原 | 结束时调用 `ChangeDisplaySettingsExW(设备, NULL, NULL, 0, NULL)` 回到用户保存的设置，并写一条操作记录 |
| 冲突 | 同一块屏幕同时只接受一个设备调整；同一设备重开会话时最多等 3 秒让旧会话先还原，其余情况回复 `applied: false` 并说明原因 |

画面尺寸变化后，正在进行的视频流按原有规则报“画面尺寸已变化”并重新同步。界面在看屏工具条上提供“对方分辨率跟随本机”开关，默认打开，记在本机。

## 自动画质

| 档位 | 最长边上限 | 目标帧率 | 目标码率 |
| --- | ---: | ---: | ---: |
| 高 | 1920 px | 60 fps | 8 Mbps |
| 中 | 1600 px | 30 fps | 3.5 Mbps |
| 低 | 1024 px | 20 fps | 1 Mbps |

后端依据实际路径往返时间、持续积累的帧延迟、发送端丢包和可用带宽估计选档。最多允许四帧在途，切换编码周期时从关键帧开始。逐步模式在空闲时仅探测连接。连续两次探测恢复后先试低档，再按持续表现提高画质。锁屏、撤销授权、暂停被控或退出时终止相应操作。

Windows 编码器随程序内置，首次使用在应用数据目录解压并验证 SHA-256。压缩资源来自 FFmpeg 9.0.2，原始构建说明和许可证保存在 `crates/platform/media` 并随解压后的程序提供。[发布构建](https://github.com/GyanD/codexffmpeg/releases/tag/9.0.2) · [对应源码](https://github.com/FFmpeg/FFmpeg/commit/946fcce07b)

发布资源为 Gyan 9.0.2 Essentials Windows x64 构建，原始 7z 的 SHA-256 为 `4705843ccaaf54257c16ad90f3e952ece33c17df964ecf7bfdbb0f49c7171077`。解压后 FFmpeg 可执行文件的 SHA-256 为 `3256173f3f8bffd7df12227c68adf68025edb1832273a9530688a7bb1ed8edec`。

## 发布版验证

以下数据来自一台 Windows 电脑上的两个独立节点。强网走本机直连；弱网测试只在测试节点上固定到本地 UDP 转发器，校验实际 RTT，防止自动选路绕过限速。

| 场景 | 测量结果 |
| --- | --- |
| 连续视频 | AMD 硬编 `h264_amf`，1920x1080。90 帧全部通过解码校验，实测 49.2 fps，接收帧间隔中位数 20.9 ms，P95 为 21.7 ms。首次视频帧等待 3.24 秒，先前已返回 JPEG 首屏 |
| 受限链路 | 下行 1 Mbps，额外单向延迟 270 ms，实测往返 280 ms。施加限制后 3.08 秒收到降级截图，解除限制后 4.49 秒收到新的可独立解码视频帧 |
| 慢接收端 | 每次取帧额外等待 900 ms 后进入逐步模式。空闲期间持续等待，一次输入返回一张 JPEG，审计计数确认没有额外发起截图请求 |
| 权限与退出 | 仅有截图权限的节点可以接收实时视频。输入被拒绝，撤销截图授权后视频停止。关闭会话取消仍在等待的取帧 |
| 回归 | Rust 发布版全工作区 62 项通过，包括三个需要真实 Windows 桌面的测试。Rust 全目标 Clippy 以警告为错误通过。原有前端 22 项测试和类型检查通过，原有文件列表保留一条 lint 提示 |

帧间隔描述接收端取得相邻画面的间隔，鼠标到显示器的整链路延迟需在接入前端的两台实体设备上另测。
